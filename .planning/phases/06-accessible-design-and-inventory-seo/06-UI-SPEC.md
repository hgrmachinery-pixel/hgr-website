## Design System

| Property | Value |
|----------|-------|
| Tool | none (existing hand-authored CSS tokens and site components) |
| Preset | not applicable |
| Component library | none; reuse existing React components |
| Icon library | none; use text/semantic controls or existing brand assets only |
| Font | Inter, with existing system sans-serif fallbacks |

Use the existing Next.js App Router and `src/app/(site)/site.css`. Centralize colors as CSS custom properties and extend existing components in place. Do not add a UI or animation dependency. ## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` | Main page background and primary content surfaces |
| Secondary (30%) | `#F5F5F5` and `#222222` | Light cards/filters and selected dark feature sections; use `#151515` for dark-section backgrounds |
| Accent (10%) | `#F86C00`; hover `#E85F00`; highlight `#F89800` | Brand marks, primary action backgrounds, and selected active accents |
| Destructive | `#A12C22` | Form failure/destructive feedback only, paired with explanatory text |

Accent reserved for: HGR logo/mark, primary CTA backgrounds with `#171717` text, active selection borders/indicators that also have a non-color state cue, and occasional large decorative accents. Never use white text on HGR orange. Do not use orange as small text on white; use `#171717` text and underlining for readable links. Use `#171717` for primary text, `#5F6368` for secondary text on light surfaces, `#FFFFFF` for text on dark surfaces, and `#D0D0D0` for secondary dark-surface text. Every text/control pairing must meet WCAG AA contrast (4.5:1 normal text, 3:1 large text and non-text controls); status must also have a readable label, not color alone. Keep focus indication separate from the orange accent: retain a 3px `#1267A5` outline with visible offset.

## Interaction and SEO Contract

- Use semantic header, navigation, main, section and footer landmarks. Preserve keyboard operation for navigation, filters, gallery category controls, gallery previous/next actions, pagination, forms and enquiry submission.
- Every input has a visible programmatic label. Errors are associated with the relevant field and announced; success is shown only after the existing adapter accepts the enquiry.
- For icon-only controls, use visible text where practical; when a control must remain icon-only, give it a clear programmatic accessible name.
- Keep a persistent visible 3px keyboard focus outline with offset. Meet WCAG AA text contrast and make every status distinguishable without color alone. Controls have at least 44×44px touch targets.
- Homepage visual anchor: use the approved real HGR excavator in the hero when an approved asset exists; keep its body/tracks visually anchored while any optional boom/arm motion remains supplemental. If no approved hero asset exists, anchor the page on the Available Excavators section and its first genuine machine photo when available; without a suitable photo, use the section heading and text as the anchor. Initial attention order is the “Used Excavators” product heading, hero/anchor visual, “View Available Excavators” action, Available Excavators cards, direct enquiry action, then secondary business promotions. Static content remains complete and usable throughout.
- Use only a verified rights-approved HGR image. If no approved image is present, omit the hero photograph and sharing image, and render the static no-image layout without placeholder machinery or fabricated claims. Motion must be disabled for `prefers-reduced-motion` and use a static/simplified small-screen and weak-device fallback.
- Build unique titles, descriptions and canonical URLs for intended public home, inventory, machine and supporting routes from verified visible content and the configured public origin. Machine title/description must be based on that specific published physical unit and omit unknown facts.
- Keep unique machine slugs tied to their physical HGR identity; a genuine corrected slug redirects to the same unit. Sold machine URLs remain reachable with truthful Sold status and no current-sale wording or stale Offer markup.
- Generate sitemap entries only from intended public canonical routes and published machine records. Exclude draft, archived, admin, API, private-document and staging content. Keep staging noindex/protected. Filter/facet query variants must not become indexable landing pages or sitemap entries; use the base inventory canonical policy for filtered views.
- Emit structured data only when it matches visible verified facts; omit hidden prices, unsupported availability, ratings, reviews, business-location facts and other unknowns. Do not add keyword volume/ranking claims or analytics/tag behavior in this phase.
- Local metadata/sitemap/robots/JSON-LD tests should assert public projection allow-listing, unique route canonicals, accurate Sold facts, no filter URLs, staging noindex, and omission of unsupported fields. Any browser/device, media delivery, deployed host and Search Console evidence belongs to the later deployment milestone.
