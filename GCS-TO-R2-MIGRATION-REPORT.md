# Remaining Google Cloud Storage Usage: Cloudflare R2 Migration Report

**Date:** 8 October 2026  
**Scope:** Read-only review of Payload collection-to-storage assignments, collection workflows, the existing R2 integration, and repository deployment/recovery records. No code or configuration was changed and no storage service was contacted.

**Superseded status note (9 October 2026):** HGR approved Cloudflare R2 for V1. The source now routes `machine-media`, `inventory-media`, and `machine-documents` through R2; the GCS adapter is retained only for the guarded local `foundation-fixtures` smoke collection. This report is a historical pre-decision snapshot. The real bucket/object inventory, any required copy, private/public delivery checks, and recovery remain unverified.

## Summary

The active Payload configuration assigns GCS to three collections unconditionally: `foundation-fixtures`, `machine-media`, and `machine-documents`. `inventory-media` uses GCS unless `INVENTORY_MEDIA_STORAGE=r2`; with that setting it is assigned to the existing S3-compatible R2 adapter. Therefore the configured GCS collection set depends on that flag.

The repository does not record an explicit decision explaining why machine photos and documents have not moved to R2. The approved project plan originally named GCS as the first storage adapter, while the R2 integration was later added only for `inventory-media`. Live GCS/R2 service acceptance is still pending, so the code assignments do not prove either provider has been used with real HGR media.

## Shared migration requirements

- Confirm the owner’s intended production provider and an already-approved isolated R2 bucket before changing assignments. No R2 account/bucket setup or live integration test is evidenced in the reviewed records.
- Inventory the current database records and object keys for each collection. Do not assume empty storage from an empty Neon database; object storage is separate from PostgreSQL.
- If objects exist, copy originals and every Payload-generated size/derivative while preserving the expected bucket key/prefix. Compare counts, sizes and checksums before changing the adapter. Retain source objects until acceptance and recovery evidence is complete.
- Verify upload, update/replacement, file delivery, missing-object behavior, cache headers, authenticated Admin access, anonymous denial, and restart persistence with synthetic files. For documents, separately prove private-original denial and approved-copy access.
- Keep GCS credentials and read access until all required objects are copied and verified. Update backup/recovery coverage so database snapshots and each object class refer to the same recovery point.
- The application currently requires GCS project and bucket configuration even when R2 is selected because the GCS adapter still serves other collections. Removing GCS entirely requires changing the collection assignments or production configuration and is outside this audit.

## Recommendation before launch

**Recommend migrating the production machine-photo and machine-document collections to R2 before launch only if HGR confirms R2 as the intended production object store and the privacy, delivery, and restore checks pass in an approved isolated environment.** Keeping two production storage providers adds configuration and recovery work, while a tested single-provider arrangement is simpler to operate.

Do **not** treat `foundation-fixtures` as launch media that must be migrated. It is synthetic test content; keep it isolated for an approved smoke test or exclude it from production through a separately reviewed configuration decision. `inventory-media` already has an R2 path, but its actual deployment and acceptance remain unverified.

There is no evidence in this review that an object copy is currently required. The database being newly created or empty would not establish that GCS buckets are empty. Check the exact approved bucket and record/object state before planning or claiming a no-copy cutover. Do not delete source objects as part of migration without separate explicit authorization.

**Overall assessment:** R2 integration is technically plausible through the existing Payload S3-compatible adapter, but a production-wide R2 cutover is **not yet verified**. The key blockers are provider/bucket approval and access, secure file-delivery acceptance for machine media and documents, object inventory/copy decisions, and matched backup/restore proof.
